# MaterialIQ — Supabase / PostgreSQL artifacts (Step 6A, DRAFT — not applied)

This directory holds the **prepared** PostgreSQL representation of the frozen
SQLite v11 schema. Nothing here is wired into the application in Step 6A: the
app still runs on `data/materialiq.db`, and **no migration has been applied to
Supabase**.

## Contents

- `migrations/20260920120000_materialiq_v11_schema.sql` — the complete draft
  schema translation (18 business tables + app-owned `_migrations`, 33 indexes,
  full CHECK/FK/UNIQUE constraint preservation).
- `rls-design.md` — RLS strategy design only. No policy SQL is applied.

## Translation rules (SQLite v11 → PostgreSQL 15)

| SQLite | PostgreSQL | Rationale |
|---|---|---|
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `bigint GENERATED BY DEFAULT AS IDENTITY` | BY DEFAULT (not ALWAYS) so the Step-6C data load can insert SQLite ids explicitly |
| `REAL` | `double precision` | equivalent 8-byte float; keeps byte-identical score semantics |
| `TEXT` ISO-8601 timestamps | `timestamptz` | native, semantically equivalent; application serializes ISO-8601 both ways |
| `INTEGER` 0/1 booleans | `boolean` | the 0/1 CHECK becomes structurally impossible — no constraint weakened |
| `strftime('%Y-%m-%dT%H:%M:%fZ','now')` | `now()` | equivalent default |
| `length(x)` | `char_length(x)` | identical semantics for text |
| partial unique `ON ((1)) WHERE …` | identical PG idiom | both `uq_matching_runs_active` and `uq_import_runs_active` kept verbatim |
| `evidence TEXT` (queryable JSON) | `jsonb` | production SQL already queries it by path — 6 `json_extract` call sites on `$.decision.state/band/reason` |
| other JSON-ish TEXT (`details`, `quality_checks`, `confusion`, `matcher_config`, `column_mapping`, `row_report`, `error_info`, `critical_difference`, `explanation`) | `text` | app code serializes/deserializes these whole; PG path queries are not used on them; TEXT avoids any reserialization-order change |

## JSON/TEXT decision summary

`match_candidates.evidence` is the **only** JSON promotion: it is the one field
with demonstrated server-side path queries. Every other JSON-like column is
stored as `text` because nothing queries inside it and the frozen application
code does whole-value `JSON.parse`/`JSON.stringify`. This is deliberately
conservative — a later step may promote columns after an audit of write paths.

## UUID / timestamp decision summary

- All existing integer identities remain `bigint` identities (ids are not
  changed "unnecessarily"). `matching_runs.id`, `import_runs.id`,
  `sessions.id` are app-generated UUID strings and stay `text PK` exactly as in
  SQLite.
- Timestamps become `timestamptz` with `now()` defaults. Values written by the
  application remain app-controlled (app-visible values unchanged).

## How this will be applied (future step — NOT now)

Supabase CLI: `supabase migration new` convention is already followed
(`migrations/<timestamp>_name.sql`). During the cutover step it will be applied
via the Supabase migration runner (or the Management API), after review and
after the RLS decisions in `rls-design.md` are approved. The application-owned
`_migrations` table is created empty here — the Step-6C data load will seed it
with versions 1–11 to mirror the SQLite registry.
